# Run Ray Sandbox on ACK

This document is intended for users who need to run Ray Sandbox on Alibaba Cloud Container Service for Kubernetes (ACK). It provides complete operational guidance from initial setup through production deployment.
All operations in this document include command-line procedures (aliyun CLI and kubectl) and have been tested and verified on an ACK managed cluster (Tokyo region, Kubernetes 1.36.2-aliyun.1).

## Background
### Ray Sandbox and gVisor
Starting with version 2.58, Ray provides the experimental `ray.experimental.sandbox` API, which allows Ray jobs to create mutually isolated sandbox containers on cluster nodes on demand and perform operations such as writing files and executing commands inside the sandboxes. This capability is suitable for scenarios in which untrusted code runs in a Ray cluster, such as code generated by large language models or scripts uploaded by users.

Ray Sandbox uses gVisor as its isolation runtime. gVisor is an open source application kernel from Google. Its core component, runsc, intercepts and handles container system calls as a user-space process, adding an isolation layer between containers and the host kernel. Ray nodes use runsc to start sandbox containers, so code executed inside a sandbox cannot directly access the host kernel.

### Two Deployment Models
Ray Sandbox can be deployed on ACK in two models, which differ in the isolation level of the Ray nodes themselves:

| Comparison | Basic model | Advanced model |
| --- | --- | --- |
| Ray node type | Standard ECS node (runc container) | ACK secure sandbox node (rund, microVM) |
| Sandbox operating mode | Rootless gVisor | Rootful gVisor |
| Isolation layers | One sandbox (gVisor) layer | Two layers: node-level microVM + sandbox (gVisor) |
| Sandbox CPU/memory limits | Do not take effect (known behavior in rootless mode) | Take effect |
| Node kernel parameter adjustment | Must enable `user.max_user_namespaces` | Not required |
| Applicable scenarios | Development, testing, and general multi-tenancy | Production environments with strong isolation requirements |

### Prerequisites
- The aliyun CLI is installed and configured (credentials have been configured with `aliyun configure`), and the account has permissions to operate ACK, ECS, VPC, and ACR.
- kubectl and Helm (optional) are installed.
- The region, cluster, instance, and other identifiers in this document are referenced through environment variables. Set them according to the following table first:


Target:

Create an ACK Managed Pro cluster in the target region. The following request body does not include an existing VPC identifier. ACK automatically creates a VPC and vSwitches in three zones, as well as a system node pool (two ecs.g9i.xlarge instances).

2. Create the cluster:

```bash

  --header "Content-Type=application/json" \
```


Expected result and stop conditions:

The output is `running` (usually after 10 to 15 minutes). If the status is `failed` or remains `initial` for a long time, stop the subsequent steps and inspect the `error_msg` field in the response body.

> Note: The aliyun CLI `cs` command must explicitly specify `--region`; otherwise, the request is sent to the default region in the CLI configuration.

### 2. Enable user.max_user_namespaces
Background:

Rootless gVisor relies on user namespaces to map root inside the container. gVisor officially requires the host's `user.max_user_namespaces` to be at least 15000,
whereas its default value is 0 in the Alibaba Cloud Linux 3 node image and must be adjusted.
The ACK node pool operating system parameter API supports rolling application to both existing and newly added nodes.

Procedure:

1. Call the node pool operating system parameter API:

```bash
aliyun cs PUT /clusters/${CLUSTER_ID}/nodepools/${GV_NODEPOOL_ID}/node_config \
  --region ${REGION} \
  --header "Content-Type=application/json" \
  --body '{"os_config":{"sysctl":{"user.max_user_namespaces":"65536"}},"rolling_policy":{"max_parallelism":1}}'
```

The `task_id` in the returned JSON identifies this rolling task.

2. After the task is complete, verify the setting on the node through Cloud Assistant. Obtain the node instance identifier with `kubectl get node <node name> -o jsonpath='{.spec.providerID}'`:

```bash
aliyun ecs RunCommand --RegionId ${REGION} --Type RunShellScript \
  --CommandContent "sysctl user.max_user_namespaces" \
  --InstanceId <node instance ID>
aliyun ecs DescribeInvocationResults --RegionId ${REGION} \
  --InvocationId <InvokeId returned in the preceding step> \
  | python3 -c 'import json,sys,base64; r=json.load(sys.stdin)["Invocation"]["InvocationResults"]["InvocationResult"][0]; print(base64.b64decode(r["Output"]).decode())'
```

Expected result and stop conditions:

The output is `user.max_user_namespaces = 65536`. If it is still 0, stop and confirm that the task status is successful.

### 3. Deploy and Verify the RayJob
#### Background: Changes to gVisor Release Artifacts
Starting with version 20260831.0, gVisor no longer publishes a standalone runsc binary and provides only the package files `gvisor.tar.zstd` (or `gvisor.tar.bz2`).
The package contains runsc, containerd-shim-runsc-v1, and the `gvisor-bin/` directory.
Under its STRICT policy, the new runsc depends on `gvisor-bin/gvisor_sentry` in the same directory. Extracting only the runsc file prevents the sandbox from starting.
The `release/latest/.../runsc` URL referenced in Ray's official `ray-job.sandbox.yaml` example no longer works after this change and returns 404.
This document uses the pinned version 20260921.0 and performs SHA-512 verification after downloading it.

Procedure:

1. Save the following content as `rayjob-basic.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: ray-sandbox
---
apiVersion: ray.io/v1
kind: RayJob
metadata:
  name: rayjob-sandbox
  namespace: ray-sandbox
spec:
  entrypoint: |
    python3 -c "
    import ray
    from ray.experimental import sandbox

    ray.init()

    sb = sandbox.create(
        image='python:3.12-slim',
        workdir='/workspace',
        cpu=1.0,
        memory='1Gi',
    )

    script = '''
    import platform
    import sys

    print('=== Hello from inside Ray Sandbox! ===')
    print(f'Python Version : {sys.version}')
    print(f'Platform       : {platform.platform()}')
    with open('/proc/meminfo') as f:
        print(f'MemTotal       : {f.readline().split()[1]} kB')
    '''
    ray.get(sb.write_file.remote('/workspace/main.py', script))

    result = ray.get(sb.exec.remote('python3 /workspace/main.py'))
    print(f'Exit code: {result.exit_code}')
    print('Sandbox output:')
    print(result.stdout)

    ray.get(sb.delete.remote())
    print('RayJob completed successfully!')
    "
  shutdownAfterJobFinishes: true
  ttlSecondsAfterFinished: 600
  rayClusterSpec:
    rayVersion: '2.58.0'
    headGroupSpec:
      rayStartParams:
        dashboard-host: '0.0.0.0'
      template:
        spec:
          nodeSelector:
            ray-sandbox: gvisor
          tolerations:
          - key: ray-sandbox
            operator: Equal
            value: gvisor
            effect: NoSchedule
          containers:
          - name: ray-head
            image: rayproject/ray:2.58.0-py312
            imagePullPolicy: IfNotPresent
            securityContext:
              seccompProfile:
                type: Unconfined
              appArmorProfile:
                type: Unconfined
            lifecycle:
              postStart:
                exec:
                  command:
                  - /bin/sh
                  - -c
                  - |
                    set -e
                    GVISOR_VERSION=20260921.0
                    URL=https://storage.googleapis.com/gvisor/releases/release/${GVISOR_VERSION}/$(uname -m)
                    cd /tmp
                    wget -q ${URL}/gvisor.tar.zstd ${URL}/gvisor.tar.zstd.sha512
                    sha512sum -c gvisor.tar.zstd.sha512
                    zstd -dc gvisor.tar.zstd | sudo tar -x -C /usr/local/bin runsc gvisor-bin
                    rm -f gvisor.tar.zstd gvisor.tar.zstd.sha512
            resources:
              requests:
                cpu: "1"
                memory: "4Gi"
              limits:
                cpu: "2"
                memory: "4Gi"
    workerGroupSpecs:
    - groupName: worker-group
      replicas: 1
      minReplicas: 1
      maxReplicas: 3
      rayStartParams: {}
      template:
        spec:
          nodeSelector:
            ray-sandbox: gvisor
          tolerations:
          - key: ray-sandbox
            operator: Equal
            value: gvisor
            effect: NoSchedule
          containers:
          - name: ray-worker
            image: rayproject/ray:2.58.0-py312
            imagePullPolicy: IfNotPresent
            securityContext:
              seccompProfile:
                type: Unconfined
              appArmorProfile:
                type: Unconfined
            lifecycle:
              postStart:
                exec:
                  command:
                  - /bin/sh
                  - -c
                  - |
                    set -e
                    GVISOR_VERSION=20260921.0
                    URL=https://storage.googleapis.com/gvisor/releases/release/${GVISOR_VERSION}/$(uname -m)
                    cd /tmp
                    wget -q ${URL}/gvisor.tar.zstd ${URL}/gvisor.tar.zstd.sha512
                    sha512sum -c gvisor.tar.zstd.sha512
                    zstd -dc gvisor.tar.zstd | sudo tar -x -C /usr/local/bin runsc gvisor-bin
                    rm -f gvisor.tar.zstd gvisor.tar.zstd.sha512
            resources:
              requests:
                cpu: "2"
                memory: "8Gi"
              limits:
                cpu: "4"
                memory: "8Gi"
```

Key points:

- The postStart hook downloads and verifies the gVisor package after each Ray container starts, then extracts both the `runsc` and `gvisor-bin` members to `/usr/local/bin`.
zstd is located in `/home/ray/anaconda3/bin` in the Ray image and is not in sudo's secure_path. Therefore, the data stream is decompressed as the regular user before the files are extracted as root through sudo.
- The container runs as the ray user (uid 1000) by default, and the sandbox operates in rootless mode (the `rootless` parameter defaults to `true`).
- seccomp and AppArmor are set to Unconfined to prevent host security policies from blocking the user namespace operations required by gVisor.

2. Deploy and poll:

```bash
kubectl apply --dry-run=client -f rayjob-basic.yaml
kubectl apply -f rayjob-basic.yaml
kubectl -n ray-sandbox get rayjob rayjob-sandbox \
  -o jsonpath='{.status.jobDeploymentStatus}/{.status.jobStatus}'
```

3. After the job is complete, view the output:

```bash
kubectl -n ray-sandbox get pods
kubectl -n ray-sandbox logs <submitter Pod name>
```

Expected result and stop conditions:

`jobDeploymentStatus` is `Complete`, `jobStatus` is `SUCCEEDED`, and the logs contain the following:

```text
Exit code: 0
=== Hello from inside Ray Sandbox! ===
Platform       : Linux-4.19.0-gvisor-x86_64-with-glibc2.41
MemTotal       : 32053100 kB
RayJob completed successfully!
```

The `Platform` field contains `gvisor`, indicating that the sandbox process is running on the gVisor kernel. `MemTotal` shows the node's total memory instead of the declared 1 GiB: in rootless mode, runsc cannot write the cgroup limit files,
and Ray silently ignores the `cpu` and `memory` parameters. This is known behavior of Ray 2.58.0 in rootless mode. To enforce limits, use the advanced model.

If `jobDeploymentStatus` is `Failed`, stop and refer to the Troubleshooting section.

## Advanced Model: Secure Sandbox Nodes + Rootful gVisor
### 1. Principles and Constraints
ACK secure sandbox (rund) runs a Pod in a lightweight virtual machine (microVM) whose guest kernel is the kangaroo kernel, isolated from the host kernel.
In ACK clusters running Kubernetes 1.35 or later, after a node pool declares `node_components: [{"name": "sandbox-runtime"}]`,
the sandboxed-container-controller component automatically creates a RuntimeClass named `sandbox`, and nested virtualization (`CpuOptions.NestedVirtualization=enabled`) is automatically enabled when node instances are purchased.
After a Ray node is scheduled to this type of node with `runtimeClassName: sandbox`, the container itself is already isolated inside a microVM.
Running runsc in rootful mode inside the container creates two isolation layers—node-level virtualization and the gVisor application kernel—and the sandbox CPU and memory limits take effect normally in rootful mode.

Constraints:

- Only instance types in the ninth-generation ECS instance families that support nested virtualization can be used, and support differs among sizes. `ecs.g9i.8xlarge` has been tested successfully; `ecs.g9i.2xlarge` returns `InvalidInstanceType.NotSupportCpuOptionsNestedVirtualization` when the node pool is created. Before creation, adjust the instance type based on the actual error returned.
- The node pool must declare `node_components: [{"name": "sandbox-runtime"}]`; otherwise, the created nodes do not have nested virtualization capability.
- The rund guest environment uses cgroup v1, and processes are placed by default in systemd slice paths containing colons (such as `kubepods.slice:...`), which runsc cannot use directly. This must be corrected in the startup script (see the bootstrap script below).

### 4. Deploy and Verify the RayJob
#### Design Highlights
1. The KubeRay annotation `ray.io/overwrite-container-cmd: "true"` stores the Ray container startup command in the `KUBERAY_GEN_RAY_START_CMD` environment variable, allowing the user to take full control of the container command.
After the bootstrap script installs gVisor and corrects the cgroup configuration, it starts Ray with `exec /bin/bash -lc "${KUBERAY_GEN_RAY_START_CMD}"`.
2. cgroup correction logic: take a snapshot of `/proc/self/cgroup`, remount each controller under `/mnt/cgreal/<name>`, create the `rsclean` subdirectory, and move the current process into it so that the process leaves the path containing colons.
This logic must run in the same shell process as the Ray startup command so that the process migration applies to its child processes.
3. KubeRay's submitter incorporates the RayJob `entrypoint` into a longer shell command. Multiline entrypoints (especially heredocs) are corrupted after concatenation.
Therefore, the example script is stored in a ConfigMap, and the entrypoint remains the single-line command `python3 /opt/ray-sandbox/entrypoint.py`.
4. The sandbox parameter `rootless: false` enables rootful mode, in which the `cpu` and `memory` limits take effect.

Procedure:

1. Save the following content as `rayjob-rund-rootful.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ray-sandbox-bootstrap
  namespace: ray-sandbox
data:
  bootstrap.sh: |
    #!/bin/bash
    set -euo pipefail

    GVISOR_VERSION=20260921.0
    URL=https://storage.googleapis.com/gvisor/releases/release/${GVISOR_VERSION}/$(uname -m)
    cd /tmp
    wget -q ${URL}/gvisor.tar.zstd ${URL}/gvisor.tar.zstd.sha512
    sha512sum -c gvisor.tar.zstd.sha512
    zstd -dc gvisor.tar.zstd | tar -x -C /usr/local/bin runsc gvisor-bin
    rm -f gvisor.tar.zstd gvisor.tar.zstd.sha512

    SNAP=/tmp/cg.snap
    CLEAN=rsclean
    REAL=/mnt/cgreal
    cat /proc/self/cgroup > "${SNAP}"
    mkdir -p "${REAL}"

    moved=0
    while IFS= read -r line; do
      rest="${line#*:}"
      ctrl="${rest%%:*}"
      [ -z "${ctrl:-}" ] && continue
      name="${ctrl//,/_}"
      name="${name//name=/sysd_}"
      mp="${REAL}/${name}"
      mkdir -p "${mp}"

      if ! mountpoint -q "${mp}"; then
        if [ "${ctrl#name=}" != "${ctrl}" ]; then
          mount -t cgroup -o "none,name=${ctrl#name=}" cgroup "${mp}" || continue
        else
          mount -t cgroup -o "${ctrl}" cgroup "${mp}" || continue
        fi
      fi

      mkdir -p "${mp}/${CLEAN}" || continue
      if [ -f "${mp}/${CLEAN}/cpuset.cpus" ]; then
        cat "${mp}/cpuset.cpus" > "${mp}/${CLEAN}/cpuset.cpus"
        cat "${mp}/cpuset.mems" > "${mp}/${CLEAN}/cpuset.mems"
      fi
      echo $$ > "${mp}/${CLEAN}/cgroup.procs" && moved=$((moved + 1))
```

## Production Practices
### 1. Build runsc into the Ray Image
Background:

Both the basic and advanced models download runsc from the gVisor release URL when the container starts, which introduces an external-network dependency and a risk of version drift. For production environments, build runsc into the image and host the image in Alibaba Cloud Container Registry (ACR).

The following environment variables are used in this section:

```bash
export ACR_INSTANCE_ID=<ACR Enterprise Edition instance ID>
export ACR_INSTANCE_NAME=<ACR Enterprise Edition instance name>
export ACR_REGION=<region of the ACR instance>
export ACR_REGISTRY=${ACR_INSTANCE_NAME}-registry.${ACR_REGION}.cr.aliyuncs.com
```

Procedure:

1. Prepare public access for the ACR Enterprise Edition instance. Enable the public endpoint:

```bash
aliyun cr UpdateInstanceEndpointStatus \
  --InstanceId ${ACR_INSTANCE_ID} \
  --EndpointType internet --Enable true \
  --region ${ACR_REGION}
```

After the public endpoint is enabled, the system writes the default whitelist entry `127.0.0.1/32` (which denies all sources). This entry overwrites any whitelist entries added before the endpoint was enabled, so add whitelist entries only after the endpoint status becomes RUNNING. The outbound address of the cluster nodes is the NAT gateway's elastic public IP address, which can be queried as follows:

```bash
aliyun vpc DescribeNatGateways --RegionId ${REGION} --VpcId ${VPC_ID} \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); [print(i["IpAddress"]) for g in d["NatGateways"]["NatGateway"] for i in g["IpLists"]["IpList"]]'
```

Add a whitelist entry:

```bash
aliyun cr CreateInstanceEndpointAclPolicy \
  --InstanceId ${ACR_INSTANCE_ID} \
  --EndpointType internet \
  --Entry <NAT elastic public IP>/32 \
  --Comment "ray-sandbox-guide egress" \
  --region ${ACR_REGION}
```

2. Create a public namespace (with automatic repository creation enabled):

```bash
aliyun cr CreateNamespace \
  --InstanceId ${ACR_INSTANCE_ID} \
  --NamespaceName kuberay-guide \
  --AutoCreateRepo true \
  --DefaultRepoType PUBLIC \
  --region ${ACR_REGION}
```

3. Obtain a temporary token for pushing and write it to a cluster Secret. The temporary token is valid for approximately one hour. Pulls return 401 after it expires, at which point you must obtain a new token and update the Secret. For production environments, use a fixed registry password or the ACR password-free component acr-credential-helper instead:

```bash
TOKEN=$(aliyun cr GetAuthorizationToken \
  --InstanceId ${ACR_INSTANCE_ID} --region ${ACR_REGION} \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["AuthorizationToken"])')
kubectl -n ray-sandbox create secret docker-registry ee-registry \
  --docker-server=${ACR_REGISTRY} \
  --docker-username=cr_temp_user \
  --docker-password="${TOKEN}" \
  --dry-run=client -o yaml | kubectl apply -f -
unset TOKEN
```

4. Use kaniko inside the cluster to build and push the image. Save the following content as `kaniko.yaml` and run `kubectl apply -f kaniko.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: kaniko-dockerfiles
  namespace: ray-sandbox
data:
  Dockerfile.rayrunsc: |
    FROM rayproject/ray:2.58.0-py312
    ARG GVISOR_VERSION=20260921.0
    USER root
    RUN set -e; \
        URL=https://storage.googleapis.com/gvisor/releases/release/${GVISOR_VERSION}/$(uname -m); \
        cd /tmp; \
        wget -q ${URL}/gvisor.tar.zstd ${URL}/gvisor.tar.zstd.sha512; \
        sha512sum -c gvisor.tar.zstd.sha512; \
        zstd -dc gvisor.tar.zstd | tar -x -C /usr/local/bin runsc gvisor-bin; \
        rm -f gvisor.tar.zstd gvisor.tar.zstd.sha512
    USER ray
---
apiVersion: batch/v1
kind: Job
metadata:
  name: kaniko-build-rayrunsc
  namespace: ray-sandbox
spec:
  backoffLimit: 0
  ttlSecondsAfterFinished: 1800
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: kaniko
        image: gcr.io/kaniko-project/executor:v1.23.2
        args:
        - --dockerfile=/workspace/Dockerfile.rayrunsc
        - --context=dir:///workspace
        - --destination=${ACR_REGISTRY}/kuberay-guide/ray-runsc:2.58.0-py312-gvisor20260921.0
        volumeMounts:
        - name: workspace
          mountPath: /workspace
        - name: docker-config
          mountPath: /kaniko/.docker
        resources:
          requests:
            cpu: "1"
            memory: "2Gi"
          limits:
            cpu: "2"
            memory: "4Gi"
      volumes:
      - name: workspace
        configMap:
          name: kaniko-dockerfiles
      - name: docker-config
        secret:
          secretName: ee-registry
          items:
          - key: .dockerconfigjson
            path: config.json
```

Note: Replace `${ACR_REGISTRY}` in the YAML above with its actual value before applying it.
If you use envsubst, specify the variable name list (for example, `envsubst '${ACR_REGISTRY}'`) to avoid unintentionally replacing build-time variables such as `${GVISOR_VERSION}` in the Dockerfile. Alternatively, write the complete address directly.

5. Confirm that the push is complete:

```bash
kubectl -n ray-sandbox logs -l job-name=kaniko-build-rayrunsc --tail=3
```

The push is successful when the logs contain `Pushed ${ACR_REGISTRY}/kuberay-guide/ray-runsc@sha256:...`.

#### Use the Built-in Image
Replace the container image in the RayJob with `${ACR_REGISTRY}/kuberay-guide/ray-runsc:2.58.0-py312-gvisor20260921.0`, remove the postStart hook, and configure `imagePullSecrets` for the Pod:

- Add `imagePullSecrets: [{name: ee-registry}]` to the head and worker Pod templates.
- KubeRay's job submitter uses the head image by default but does not inherit `imagePullSecrets` from rayClusterSpec.
You must explicitly provide `submitterPodTemplate` in the RayJob. This template must include `restartPolicy: Never` and a container definition named `ray-job-submitter`; otherwise, validation fails and the submitter Job cannot be created:

```yaml
spec:
  submitterPodTemplate:
    spec:
      restartPolicy: Never
      imagePullSecrets:
      - name: ee-registry
      containers:
      - name: ray-job-submitter
        image: <ACR_REGISTRY>/kuberay-guide/ray-runsc:2.58.0-py312-gvisor20260921.0
```

This configuration has been tested and verified: the head, worker, and submitter can all pull the image from the ACR Enterprise Edition instance and complete the job.

### 2. Comparison of Image Hosting and Pull Methods
The Ray Sandbox workflow has two types of image consumers, with different pull mechanisms and repository requirements:

| Consumer | Pull mechanism | Docker Hub public repository | ACR public repository | ACR private repository |
| --- | --- | --- | --- | --- |
| Ray node image (kubelet/containerd) | containerd, supports imagePullSecrets | Supported (tested) | Supported (with imagePullSecrets, tested) | Supported (with imagePullSecrets) |
| Sandbox image (Ray puller) | Registry v2 HTTP API + anonymous Bearer token; credentials are not supported | Supported (tested) | Requires anonymous pull capability: public repositories in Personal Edition support it by default; for Enterprise Edition, enable "Public Anonymous Pull" on the instance overview page in the console | Not supported (Ray 2.58.0) |

Test record: When "Public Anonymous Pull" is not enabled for an Enterprise Edition instance, an anonymous pull from a public repository returns `401 UNAUTHORIZED` (a token can be issued but does not include pull permission).
For the location of the Enterprise Edition anonymous pull switch, see the ACR documentation "Why does anonymous image pulling fail for an Enterprise Edition instance?"
The Ray 2.58.0 image puller (the internal implementation of `ray.experimental.sandbox`) only performs anonymous token exchange and provides no credential configuration entry point, so it cannot pull from any repository that requires authentication. To use a sandbox image from a private repository, use the preloading method in the next section.

### 3. Preload a Sandbox Image tar Archive
Background:

When the sandbox image is in a private repository, or when you want to eliminate runtime external-network dependencies entirely, flatten the image into a tar archive and preload it onto the node, then point the `image` parameter of `sandbox.create` to the tar path on the node. Ray directly extracts this tar archive as the sandbox root filesystem.

Note: In tar mode, the image does not carry image configuration (environment variables or working directory). The `env` field in the OCI configuration generated by Ray is an empty array, leaving `PATH` empty inside the sandbox so that the `sleep` daemon cannot be found. You must explicitly inject `PATH` in `sandbox.create`.

Procedure:

1. Use crane to flatten and export the image to a node directory. Save the following content as `crane-export.yaml` and run `kubectl apply -f crane-export.yaml`:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: crane-export-python
  namespace: ray-sandbox
spec:
  backoffLimit: 1
  ttlSecondsAfterFinished: 1800
  template:
    spec:
      restartPolicy: Never
      nodeSelector:
        ray-sandbox: gvisor
      tolerations:
      - key: ray-sandbox
        operator: Equal
        value: gvisor
        effect: NoSchedule
      containers:
      - name: crane
        image: gcr.io/go-containerregistry/crane:v0.21.9
        args: ["export", "python:3.12-slim", "/images/python-3.12-slim.tar"]
        securityContext:
          runAsUser: 0
        volumeMounts:
        - name: images
          mountPath: /images
        resources:
          requests:
            cpu: "0.5"
            memory: "512Mi"
          limits:
            cpu: "1"
            memory: "1Gi"
      volumes:
      - name: images
        hostPath:
          path: /var/lib/ray-sandbox-images
          type: DirectoryOrCreate
```

2. Mount this directory into the containers in the RayJob head and worker Pod templates, point the sandbox image to the tar path, and inject `PATH`:

```yaml
          containers:
          - name: ray-head
            volumeMounts:
            - name: sandbox-images
              mountPath: /opt/sandbox-images
          volumes:
          - name: sandbox-images
            hostPath:
              path: /var/lib/ray-sandbox-images
              type: Directory
```

```python
sb = sandbox.create(
    image='/opt/sandbox-images/python-3.12-slim.tar',
    workdir='/workspace',
    cpu=1.0,
    memory='1Gi',
    env={'PATH': '/usr/local/bin:/usr/bin:/bin'},
)
```

This method has been tested and verified. In a multi-node environment, ensure that the tar file exists on every node that runs a Ray container. You can distribute it with a DaemonSet or bake it into the node image.

## Troubleshooting
### runsc Startup Failure: `sidecar "gvisor_sentry" not usable ... --sidecar-usage-policy is set to STRICT`
Cause: Starting with version 20260831.0, gVisor switched to package-based releases, and runsc under its STRICT policy depends on `gvisor-bin/gvisor_sentry` in the same directory.
Extracting only the runsc file (including continued use of the invalid `release/latest/.../runsc` download URL in Ray's official example) triggers this error.

Resolution: Download `gvisor.tar.zstd`, extract both the `runsc` and `gvisor-bin` members, and perform SHA-512 verification after downloading.

### Sandbox Creation Failure: User Namespace-Related Error
Cause: Rootless mode requires the host's `user.max_user_namespaces` to be at least 15000, whereas the default value in the Alibaba Cloud Linux 3 node image is 0.

Resolution: Set it to 65536 through the node pool operating system parameter API (see Section 2 of the Basic Model). The setting applies to both existing and newly added nodes.

### runsc Failure in the Advanced Model: cgroup Path Contains Colons
Cause: The rund guest uses cgroup v1, and processes are placed by default in systemd named paths in the form `kubepods.slice:...`; runsc cannot manage cgroups under such paths.

Resolution: Use the bootstrap script from Section 4 of the Advanced Model to remount each controller and move the current process to a normalized path before starting Ray. The correction logic must run in the same shell process as the Ray startup command.

### RayJob Submitter Logs Show a SyntaxError or a Missing heredoc Terminator
Cause: The KubeRay submitter incorporates the `entrypoint` into a longer shell command (prefixed with health checks and `ray job submit`, and suffixed with `ray job logs`). For a multiline entrypoint, concatenation breaks the quoting levels; for an entrypoint ending in a heredoc, the terminator line is contaminated by the concatenated content and becomes invalid.

Resolution: Put the entrypoint script in a ConfigMap and mount it into the Ray container. Keep `entrypoint` as a single-line command (such as `python3 /opt/ray-sandbox/entrypoint.py`).

### RayJob Stalls at Initializing: FailedToCreateRayJobSubmitter
View events with `kubectl -n ray-sandbox describe rayjob <name>`.
If the message is `spec.template.spec.restartPolicy: Required value`, `submitterPodTemplate` is missing `restartPolicy: Never`.
The template must also contain a container definition named `ray-job-submitter`.

### Pulling an ACR Enterprise Edition Image Returns 401
- Error `insufficient_scope: authorization failed` (anonymous pull without credentials): "Public Anonymous Pull" is not enabled for the Enterprise Edition instance. Enable it on the instance overview page in the console, or configure imagePullSecrets for the Pod.
- Error `401 Unauthorized` (with credentials): The temporary token has expired (its validity period is approximately one hour). Run GetAuthorizationToken again and update the Secret. For long-term use, configure a fixed registry password or acr-credential-helper.

### Public Endpoint Remains Unreachable After Adding an ACR Whitelist Entry
When public endpoint enablement completes, it writes the default entry `127.0.0.1/32` and overwrites the existing whitelist. After the endpoint status is RUNNING, use `ListInstanceEndpoint` to confirm the whitelist contents, and then add the actual entry.

### Secure Sandbox Node Pool Creation Fails: InvalidInstanceType.NotSupportCpuOptionsNestedVirtualization
The selected instance type does not support nested virtualization. Only some instance types in the ninth-generation ECS instance families support it (`ecs.g9i.8xlarge` was tested successfully, while `ecs.g9i.2xlarge` was not). Switch instance types and try again.

### aliyun CLI Request Error
- Zone or region mismatch: The `cs` command does not explicitly specify `--region`, so the CLI configuration region is used by default.
- `InvalidProtocol.NeedSsl`: Component management APIs require HTTPS. Add `--secure`.

## Clean Up Resources
Clean up in the following order to avoid leaving billable resources behind:

1. Delete the workloads and namespace:

```bash
kubectl delete namespace ray-sandbox
```

2. Delete the node pools (first wait for the nodes in the node pools to be drained):

```bash
aliyun cs DELETE /clusters/${CLUSTER_ID}/nodepools/${GV_NODEPOOL_ID} --region ${REGION}
aliyun cs DELETE /clusters/${CLUSTER_ID}/nodepools/${RUND_NODEPOOL_ID} --region ${REGION}
```

3. Delete the cluster:

```bash
aliyun cs DELETE /clusters/${CLUSTER_ID} --region ${REGION}
```

4. Clean up ACR resources (as needed):

```bash
aliyun cr DeleteRepository --InstanceId ${ACR_INSTANCE_ID} --RepoId <repository ID> --region ${ACR_REGION}
aliyun cr DeleteNamespace --InstanceId ${ACR_INSTANCE_ID} --NamespaceName kuberay-guide --region ${ACR_REGION}
aliyun cr DeleteInstanceEndpointAclPolicy --InstanceId ${ACR_INSTANCE_ID} --EndpointType internet --Entry <entry> --region ${ACR_REGION}
aliyun cr UpdateInstanceEndpointStatus --InstanceId ${ACR_INSTANCE_ID} --EndpointType internet --Enable false --region ${ACR_REGION}
```
