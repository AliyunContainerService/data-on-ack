# Deploy a Basic Ray Service

This guide shows how to deploy a basic Ray Serve application on an ACK cluster via the KubeRay `RayService` custom resource, and how to access and update it.

A `RayService` manages two things for you:

- A `RayCluster` that hosts the Serve application.
- The Ray Serve application itself, described declaratively in `serveConfigV2`. KubeRay deploys the application onto the cluster, monitors its health, and performs zero-downtime upgrades when the configuration changes.

## Prerequisites

- [ACK managed cluster](https://help.aliyun.com/zh/ack/ack-managed-and-ack-dedicated/user-guide/create-an-ack-managed-cluster-2)
- [KubeRay Operator](https://help.aliyun.com/zh/ack/cloud-native-ai-suite/use-cases/ack-install-kuberay-components) installed in the cluster

## About the Example

The example deploys a minimal HTTP application. The Serve application code lives in a ConfigMap (`ray-serve-app`) that is mounted into both the head and worker pods, and `PYTHONPATH` points at the mount path so Serve can import it. This keeps the example fully self-contained: no custom image build and no external `working_dir` download is required.

```python
from ray import serve
from starlette.requests import Request


@serve.deployment
class Greeter:
    async def __call__(self, request: Request) -> str:
        name = request.query_params.get("name", "Ray")
        return f"Hello {name} from Ray Serve!"


app = Greeter.bind()
```

The `serveConfigV2` section tells KubeRay to deploy this module as an application with 2 replicas:

```yaml
serveConfigV2: |
  applications:
    - name: greeter
      import_path: greeter:app
      route_prefix: /
      deployments:
        - name: Greeter
          num_replicas: 2
          ray_actor_options:
            num_cpus: 0.5
```

> For production workloads, the recommended practice is to bake your application code into a custom container image instead of a ConfigMap, or use `runtime_env.working_dir` pointing to a package on OSS.

## 1. Deploy the RayService

```bash
kubectl apply -f ray-service.yaml
```

Expected output:

```
configmap/ray-serve-app created
rayservice.ray.io/demo-ray-service created
```

Wait for the RayService to become ready (this creates the RayCluster, starts Serve, and deploys the application; it usually takes a few minutes):

```bash
kubectl get rayservice demo-ray-service -w
```

Expected output (wait until `SERVICE STATUS` is `Running`):

```
NAME               SERVICE STATUS   NUM SERVE ENDPOINTS
demo-ray-service   WaitForServeDeploymentReady
demo-ray-service   Running          2
```

Check the pods and services created by KubeRay:

```bash
kubectl get pods -l ray.io/serve=true
kubectl get svc | grep demo-ray-service
```

Expected output (the `-rq2wc` style suffix is generated by KubeRay and varies):

```
NAME                                                 READY   STATUS    RESTARTS   AGE
demo-ray-service-rq2wc-head-jvhf2                    1/1     Running   0          11m
demo-ray-service-rq2wc-worker-group-worker-2kv2v     1/1     Running   0          11m

demo-ray-service-head-svc         ClusterIP   None             <none>   10001/TCP,8265/TCP,6379/TCP,8080/TCP,8000/TCP   2m
demo-ray-service-rq2wc-head-svc   ClusterIP   None             <none>   10001/TCP,8265/TCP,6379/TCP,8080/TCP,8000/TCP   11m
demo-ray-service-serve-svc        ClusterIP   192.168.46.223   <none>   8000/TCP                                        2m
```

Note that KubeRay creates a dedicated **serve service** (`demo-ray-service-serve-svc`) that only routes traffic to pods with healthy Serve proxies. Always use this service (not the head service) to access the application.

## 2. Check Serve Application Status

The Serve application status is reflected in the RayService resource:

```bash
kubectl describe rayservice demo-ray-service
```

Expected output (abbreviated, the application and deployment both show `RUNNING`/`HEALTHY`):

```
Status:
  Active Service Status:
    Application Statuses:
      greeter:
        Serve Deployment Statuses:
          Greeter:
            Status:  HEALTHY
        Status:      RUNNING
```

You can also inspect it with the Serve CLI inside the head pod:

```bash
HEAD_POD=$(kubectl get pod -l ray.io/node-type=head,ray.io/serve=true -o jsonpath='{.items[0].metadata.name}')
kubectl exec -it $HEAD_POD -- serve status
```

Expected output:

```
proxies:
  ...: HEALTHY
applications:
  greeter:
    status: RUNNING
    deployments:
      Greeter:
        status: HEALTHY
        replica_states:
          RUNNING: 2
```

## 3. Access the Ray Service

Test the application from inside the cluster through the serve service:

```bash
kubectl run curl-test --rm -it --restart=Never --image=curlimages/curl -- \
  curl -s "http://demo-ray-service-serve-svc.default.svc.cluster.local:8000/?name=ACK"
```

Expected output:

```
Hello ACK from Ray Serve!
```

Or port-forward to your local machine:

```bash
kubectl port-forward svc/demo-ray-service-serve-svc 8000:8000
curl -s "http://127.0.0.1:8000/?name=ACK"
```

To expose the service outside the cluster, change the service to a LoadBalancer or create an Ingress; see [Expose applications in ACK](https://help.aliyun.com/zh/ack/ack-managed-and-ack-dedicated/user-guide/expose-applications).

## 4. Update the Serve Application (In-Place Update)

Updating `serveConfigV2` triggers an in-place application update without recreating the RayCluster. For example, change the number of replicas from 2 to 3:

```bash
kubectl patch rayservice demo-ray-service --type merge -p '
spec:
  serveConfigV2: |
    applications:
      - name: greeter
        import_path: greeter:app
        route_prefix: /
        deployments:
          - name: Greeter
            num_replicas: 3
            ray_actor_options:
              num_cpus: 0.5
'
```

Verify the new replica count:

```bash
kubectl exec -it $HEAD_POD -- serve status | grep -A2 replica_states
```

Expected output:

```
        replica_states:
          RUNNING: 3
```

If you change `rayClusterConfig` instead (e.g. the image), KubeRay performs a **zero-downtime upgrade**: it creates a new RayCluster, waits until the application is ready there, switches traffic, and then tears down the old cluster.

## Cleanup

```bash
kubectl delete -f ray-service.yaml
```
